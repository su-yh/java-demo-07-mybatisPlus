

## 背景

针对操作记录详情表，里面有一个before_sql字段，在出问题的时候，用来兜底恢复数据。对于该字段，要保证100%正确。





## 场景示例

两个用户同时操作，并且在数据库层面都添加了事务控制。

| 时间顺序 | 事务 A（用户 1）                                             | 事务 B（用户 2）                                             | 问题核心                                                     |
| :------: | ------------------------------------------------------------ | ------------------------------------------------------------ | ------------------------------------------------------------ |
|    1     | 开启事务，查询审核状态：`SELECT review FROM svip_add_or_update_card_no_record WHERE id=1` → 得到 `0-待审核` | -                                                            | 两事务均读取到 “旧数据 0-待审核”                             |
|    2     | -                                                            | 开启事务，查询审核状态：`SELECT review FROM svip_add_or_update_card_no_record WHERE id=1` → 得到 `0-待审核` | 读取操作无互斥，导致 “脏读” 基础上的后续错误                 |
|    3     | 业务逻辑：如果 review = 0 (待审核) 则可以执行更新操作        | -                                                            | 基于旧数据计算                                               |
|    4     | -                                                            | 业务逻辑：如果 review = 0 (待审核) 则可以执行更新操作        | 同样基于旧数据计算                                           |
|    5     | 执行更新：`UPDATE svip_add_or_update_card_no_record SET review=2 WHERE id=1`，提交事务<br />审核拒绝 | -                                                            | 事务 A 先提交，审核拒绝                                      |
|    6     | -                                                            | 执行更新：`UPDATE svip_add_or_update_card_no_record SET review=1 WHERE id=1，提交事务<br />审核通过 | 事务 B 后提交，审核通过<br />覆盖事务 A 的结果，最终结果为审核通过<br />而预期的结果应该是审核拒绝，审核通过报错提示。 |



## 原因

在高并发场景下，虽然我们使用了事务控制，但是由于在更新之前有不少业务逻辑需要判断，所以会先进行查询，通过查询的结果来判断是否更新。

也就是典型的业务场景：`查询` -> `业务逻辑判断` -> `更新`

在这种情况，高并发场景下会出现更新丢失问题，也就是只保留了最后一个更新的结果，前面几个的更新都会被最后一次更新覆盖。



## 解决方案

针对以上的情况，有几种方式可以解决。

1. 修改事务控制级别为**SERIALIZABLE**（串行化）

    - 数据库服务端设置

        事务控制级别可以在数据库服务端设置，但是这个会影响所有数据库，不能针对某个单一库

    - 客户端连接处配置

        在客户端连接处配置，优先级会高级数据库服务端的设置。

        但是只对该连接有效

    串行化 事务隔离级别会影响事务控制的性能，它是将所有的事务强行按顺序执行。

2. 使用`乐观锁`

    乐观锁需要在代码层面实现，同时每张表都需要添加一个用于控制修改序号的字段，比如：version

    同时需要同步，所有操作该表的地方都要使用乐观锁操作相同的表。

    这种方式，在spring boot 的mybatis plus 组件，已有相关的实现，如果使用需要添加相关配置以及按规范使用。

3. 使用`悲观锁`

    悲观锁也需要在代码层面实现，它的主要逻辑是在查询的时候添加  'for update' 控制。

    这个就比较麻烦了，因为相关的查询都需要添加 for update 的控制，代码层面的修改非常多，同时代码也不好控制。



鉴于以上三种实现方式，推荐使用**方案1**，同时在客户端连接处添加事务控制配置，指定为串行化
